### Autopilot-stack

**You own the stack, never the landing. Build and verify the queue with bounded autonomy, then hand the operator one linear reviewed chain she lands herself.** For "autopilot-stack", "stack them, don't ship", and "build the stack, I'll land it". The sibling of **Autopilot-full**. The owner and verification rules are the same; only the terminal differs. Nothing auto-ships.

1. **Run the owner workflow.** Assign each PR to a named agent, native subagent, or Kiro cloud session as described in `./autopilot-full.md`. Each owner gets an exclusive branch, builds and self-proves the change, triages review comments per `../references/bugbot-triage.md`, reviews prose and comments, drives the PR green per `./babysit.md`, and writes a repository decision log.
2. **Audit at bounded checkpoints.** While the active session or cloud session remains available, inspect branches, PRs, checks, and durable reports at the declared cadence. Re-read this playbook from the current branch. If an owner exceeds its timebox without side effects, stop it and start a fresh worker from its stored brief. A closed local session does not wake itself; the branch, decision log, and handoff command carry the work.
3. **Hold operator gates.** A request to state the plan is not a go. Start only on explicit approval. In Kiro CLI, `/goal` may be used only as a CLI-specific bounded cycle with finite `--max`. On stop, every owner takes an immediate zero-writes hold.
4. **Verify at stack-ready.** At each exact head SHA, fan out independent verifier subagents that rerun gates, exercise load-bearing behavior with the UI, CLI, test, shell, diagnostics, screenshot, or MCP tools actually available, and audit the receipts and diff. Fan their reports into one parent verdict. Findings return to the owner; nothing enters the chain unverified.
5. **Append on a clean verdict, never ship.** No owner merges, arms automatic merge, or closes. Append PRs in verified order or the order the operator specified.
6. **Use one topology writer.** Graphite is optional. When the repository already uses it, one designated owner serializes `gt` operations and verifies parentage before submit or restack. Otherwise build the chain with ordinary git branches and `gh` PRs, each PR targeting its intended parent branch. Record the ordered root, tip, parent, and head SHA in the repository decision log.
7. **Absorb drift, then re-verify what moved.** Update the chain from trunk using the repository's established workflow. Any rewrite changes SHAs and voids old verdicts. Compare patch IDs when available; every changed patch returns to step 4.
8. **Deliver the chain.** The deliverable is one linear chain of verified PRs, reviewable bottom-up on the hosting platform, with each verifier verdict recorded on its PR. The operator reviews and lands it using Graphite when installed or ordinary `gh pr merge` in dependency order.

**Choosing between the autopilots.** Autopilot-full when PRs are independent and merge authority is granted. Autopilot-stack when the operator wants review before landing, work is sequenced or coupled, or merge authority is withheld.

**Reply:** links to the chain root and tip, a one-line verdict per link, the topology mechanism used, and anything parked or excluded with the reason.
