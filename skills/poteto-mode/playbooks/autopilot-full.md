### Autopilot-full

**You own the verdicts, never the PRs. One owner runs each PR from build to merge, and nothing merges without your clean fan-in verdict.** For "autopilot this queue", "full autopilot", and one-owner-per-PR programs. The job is a queue of independent PRs handed over to drive to merged with bounded autonomy. Orchestrate runs a standing program whose coordinator lands verified work itself and whose workers never merge; here each PR's owner carries the whole lifecycle through merge, and the parent keeps verification, countersigns, and audits.

1. **Mark the operator's items and honor state-then-wait.** Items the operator names stay hers. She reviews and clicks, and no owner merges one. When she asks for the protocol or plan, deliver it and stop. Execution starts only on her explicit go. In Kiro CLI, `/goal` may be used as a CLI-specific bounded implementation cycle with a finite `--max`; it is not a persistence guarantee.
2. **Assign one owner per PR with the full lifecycle.** Use a named custom agent or native subagent for work that fits the attached session. Use a Kiro cloud session when an owner must continue detached and remain available across supported surfaces. Each owner gets an exclusive branch or worktree, builds the change, proves it on the real artifact, triages review comments per `../references/bugbot-triage.md`, reviews prose and comments, updates from current trunk, drives the PR green per `./babysit.md`, and leaves a repository decision log. Every brief names scope, acceptance, checks, stop conditions, and the merge gate.
3. **Run independent owners in parallel and never stack them accidentally.** One writer per branch, disjoint files, and drift absorbed before merge. Only overlapping work serializes. Self-contained PRs branch from main; sequenced work is merge-then-branch. Graphite is optional. If the repository uses it, register PRs without turning independent work into a stack. Otherwise use ordinary git branches and `gh` PRs.
4. **Fan out verification at every merge-ready head.** At the owner's exact head SHA, run independent verifier subagents and fan their evidence back into one parent verdict. Re-run gates at that SHA, exercise the load-bearing behavior with the UI, CLI, test, shell, diagnostics, screenshot, or MCP tools actually available, and audit receipts plus diff without trusting the PR body. No merge without the parent's clean verdict. Findings return to the owner; a changed head gets a fresh verdict.
5. **Merge only the authorized head.** The owner updates from trunk before the merge-ready report. If trunk moves again, the patch-id rule in `./shipping.md` governs re-verification. The owner squash-merges its own PR only after the parent verdict and explicit program-level merge authority. Operator-owned items stop at merge-ready.
6. **Audit in bounded checkpoints.** At a declared cadence while the session or cloud session is active, re-read this playbook and the repository decision log, inspect branches, PRs, checks, and verifier reports, and publish the queue table. Count commits, pushes, PR state, checks, and durable reports as progress. If a lane exceeds its timebox without a side effect, stop it and start a fresh worker from the stored brief. A local session that closes does not keep auditing; leave the branch, log, and exact resume action instead.
7. **Stand down instantly on the operator's stop.** Send every active owner a zero-writes instruction. Preserve their branches and reports. Do not merge, delete, or relaunch them.

**Reply:** the queue with each PR's owner, state, and head SHA; each verdict and its evidence; what merged and what each owner took next; countersigns granted and why; open operator gates; the repository decision-log paths.
